# CLAUDE.md (User-level / Home)

すべての Claude Code セッションで読み込まれる、ユーザー個人のグローバル設定。
プロジェクト固有の指示は各プロジェクト直下の `CLAUDE.md` に書く。

## 言語

- 日本語で応答する。

## 一般的なふるまい

- 不要な前置きや末尾の要約は省く。差分やコマンド出力で伝わることを文章で繰り返さない。
- 不確実な点を勝手に推測で埋めず、必要なら短く確認する。
- 大きな副作用を伴う操作（破壊的な git 操作、外部システムへの送信など）は事前に確認する。

## コードコメント

コメントは既定でゼロ。書くのは「コード・型・テスト・git 履歴から復元できない情報」だけ。

### 書くもの（Why）

- 設計判断の根拠と、採用しなかった代替案の理由
  - 例: `# 件数上限20なので JOIN より N+1 の方が速い（計測済み）`
- 定数・マジックナンバーの出典と、変更時の影響範囲
  - 例: `RETRY_MAX = 3  # SLA 99.9% に必要な上限。変更時はインフラチームと要協議`
- 制約・前提条件（呼び出し側がロック取得済み、単位、実行順序の依存など）
- 回避策・落とし穴（一見不要に見えるコードが消されないように）
  - 例: `# Safari 17 の IndexedDB バグ回避。修正後は削除可 https://bugs.webkit.org/...`
- 業務・法務・外部仕様への参照
  - 例: `if elapsed > 30:  # 割引期間30日は消費者契約法に基づく。法改正時に要更新`
- 公開関数の docstring は契約（引数の意味・単位、戻り値、副作用、例外）のみ。実装手順は書かない

### 書かないもの（What / 経緯）

- コードを言い換えただけのコメント（`# ユーザーを取得する` の直上に `User.find(id)`）
- 変更の経緯や旧実装との比較（`# 従来は同期だったが非同期化`、`# ○○対応で追加`）→ コミットメッセージに書く
- 「適切に」「念のため」「エッジケース対応」→ 条件と理由を具体的に書く。書けないならコメント自体を消す
- 区切り線・`# Step 1:` 形式の見出し → 関数に分割する
- コメントアウトした旧コード → 削除する（git にある）
- AI との会話 URL、「AI の説明によると」への言及 → 一次情報（issue、RFC、バグトラッカー）に置き換える
- 依頼していない TODO の追加。書く場合は issue 番号か回収条件を必須にする
  - 例: `# TODO(#1234): テクスチャストリーミング実装後に最適化`

### 既存コメントの扱い

- 引数・戻り値・挙動を変えたら、対応する docstring・コメントを同じ変更で更新する。触れないコメントは既存のまま残す
- 一時的なコードには EOL 時期と削除条件を書く
  - 例: `# v1 API からの変換。2026-09 EOL。EOL 後に本関数とテストを削除`

## 環境

- dotfile は `chezmoi` で管理しており、元のファイルは `~/git/dotfiles` リポジトリ以下にある。`$HOME` 側を直接編集してもソースには反映されないので、必ずリポジトリ側を編集する。
- `mise` がインストールされており、node・python などのランタイムを管理している。
