# parallel-code-review

任意のスコープに対する建設的なコードレビューを行う。

質の担保は **観点別 finder の並列 fan-out → 指摘ごとの検証・confidence 採点 → 閾値フィルタ** で行う。単発の順次チェックはリスクの高い変更を見落としやすいため、非自明な差分では必ず fan-out する。

## レビュー対象の決定

ユーザーの指示と引数から、レビュー対象を確定する。曖昧な場合は推論し、確認を取る。

PR をレビューする場合でも、**GitHub 上にコメントは投稿しない**。結果は会話に返す。PR の場合のみ finder F6（過去 PR コメント）が追加で有効になる。

### 過去のレビュー指摘（再レビュー時）

`--prev <path>`、またはプロンプト中の `## 過去のレビュー指摘` ブロックで渡される。次を守る:

- **`見送り (ユーザー決定)` と `記録のみ` は再指摘しない。**
- それ以外に解消済み、未解消など書かれていても信頼せず、実際の差分をベースにレビューする。

### 優先度表記の指定

`P0`/`P1`/`P2`/`P3` での出力を求められた場合は、通常の見出しの代わりに次の対応で出す。

| 本スキルの区分 | P 表記 | 意味 |
|---|---|---|
| 重大な問題 (Critical) | `P0` | 正しさ・セキュリティ・データ損失・リリースブロッカー |
| 重要な指摘 (Important) | `P1` | 実害のあるバグ、契約違反、リグレッションリスク、必要なテストの欠落 |
| 重要な指摘 (Important) のうち、実害が保守性・一貫性・設計に留まるもの | `P2` | 完了前に直すべきだが、動作は壊れていない |
| Nits | `P3` | 任意対応 |

confidence 80 のゲートは `P0`/`P1`/`P2` に適用する。

### 分類の要求

`(a) 今回の変更起因 / (b) 既存 / (c) スコープ外` の分類を求められた場合、各指摘に分類を付ける。

- **(a)**: レビュー対象の差分が作り出した、または悪化させた問題。
- **(b)**: 変更前から存在し、差分が悪化させていないもの。
- **(c)**: 指示された「レビュー対象外」に属するもの。

分類が要求された場合に限り、通常なら捨てる (b)/(c) を **`## 差分外・スコープ外の観察`** として末尾に別掲する（最大10件、1件1〜2行、修正案は書かない）。この節の項目は**指摘の件数に数えない**。分類が要求されていない場合は (b)/(c) は出力しない。

## レビュー観点（優先度順）

### 1. 正しさ（Correctness）
- ロジックバグ、オフバイワン、null/undefined ハンドリング漏れ
- 競合状態、並行処理の問題
- 型の不整合、暗黙の型変換による事故
- エラーハンドリング漏れ、握り潰し
- エッジケース（空配列、最大値、Unicode、タイムゾーン、負数 など）
- **終端性・状態遷移（最重要リスク）**: ループ条件 / ポーリング述語 / リトライ・バックオフ / 再帰の停止条件 / `while`・`useEffect`・購読の解除条件を変更した場合は、必ず「**どの状態でこれが停止しないか**」を明示的に答える。enum / status を条件に使う変更は、**全ての値を列挙し、変更後のロジックと消費側（表示・分岐）のロジックの両方に通して**、2 つの契約が一致するかを確認する（例: `status` の各値 ×「ポーリングする?／表示する?」の対応表を作ると、片方だけ真になる矛盾が浮く）。

### 2. セキュリティ
- 入力検証漏れ（SQL/コマンド/パスインジェクション、XSS、SSRF）
- 認証・認可の抜け
- シークレット・トークンの平文ログ出力やコミット
- 安全でない暗号、弱い乱数

### 3. 仕様・契約
- 既存の API/関数のシグネチャ変更による破壊的影響
- 後方互換性、マイグレーション漏れ
- 設定ファイル・スキーマ・テンプレート間の整合性
- ドキュメントとの乖離
- **兄弟実装との契約整合**: 同種のパターン（同じ composable ファミリ、同じ Hook、同じ base クラスの他実装）を grep し、変更後のコードがその確立された契約に一致するかを確認する。スタイルの一貫性ではなく「正しい振る舞いの契約」を兄弟から復元する。

### 4. テスト
- 重要な分岐がテストされているか
- テストが本物の振る舞いを検証しているか（ただのスナップショット/モック確認になっていないか）
- フレイキー要因（時間、ランダム、外部依存）
- ハッピーパスのみで終わっていないか

### 5. 可読性・保守性
- 命名、関数のスコープ、責務の分離
- 過剰な抽象化／早すぎる一般化
- 重複コード、Magic Number
- コメントが「なぜ」を語っているか（「何を」を冗長に書いていないか）

### 6. パフォーマンス
- 明らかな N+1、不要なループ・コピー
- ホットパスでのアロケーション
- 不必要な同期 I/O、ブロッキング
- ※ 計測根拠のないマイクロ最適化は提案しない

## 実行フロー

### Step 1: スコープと差分の取得

`git diff --stat <range>` で変更規模を掴み、`git diff <range>` で全体差分を取る。PR の場合は `gh pr diff` / `gh pr view` で差分と説明を取得する。

### Step 2: プロジェクト規約の確認

`CLAUDE.md`、`AGENTS.md`、`.github/PULL_REQUEST_TEMPLATE.md`、`README.md` のうち存在するものと、変更ファイルのディレクトリ直下の `CLAUDE.md` を読む。プロジェクト固有のルールを優先する。

### Step 3: 周辺コードの読み込み

差分だけでは判断できない場合、呼び出し元・呼び出し先、型定義、設定ファイル、兄弟実装など判断に必要な範囲を読む。**差分外の文脈を読まずにコメントしない。**

### Step 4: fan-out（観点別 finder を並列 spawn）

差分の規模に応じて **4〜6 個の finder サブエージェント**を Agent / Task ツールで**同時に** spawn する（1 メッセージ内で複数 spawn）。各 finder にはレビュー対象の range と、下記の担当レンズだけを渡し、**指摘の一覧**を構造化して返させる。各指摘は `{ file:line, 要約, 根拠(参照した行・履歴・兄弟実装), 想定失敗シナリオ }` を必須項目とする。

- **F1 規約準拠**: `CLAUDE.md` / `AGENTS.md` / 近傍のコード内コメントに反していないか。規約が**その箇所を明示的に指している**場合のみ指摘する（一般論の押し付けはしない）。
- **F2 バグ走査**: 差分そのものを中心に、素朴なバグを走査。大物優先。nit・linter/型検査で機械的に捕まるもの・明白な誤検知は出さない。
- **F3 履歴文脈**: `git blame` / `git log -p` で変更行の来歴を読み、過去の意図・過去の修正を壊していないか（一度直したバグの再導入など）を確認。
- **F4 状態・制御フロー**: ループ終端 / ポーリング・リトライ条件 / async・並行 / enum・status の網羅性。「どの状態で停止しないか」「全状態を変更後ロジックと消費側の両方に通したか」を必ず回答に含める。
- **F5 契約・整合**: 呼び出し元 / 型 / スキーマ / 設定 / 兄弟実装との齟齬。同種パターンの既存実装を grep して契約を復元し、変更がそれに一致するかを検証。cross-file の破壊（rename の取り残し、stale 参照）も担当。
- **F6 過去 PR コメント（PR レビュー時のみ）**: 当該ファイルを触った過去 PR のレビューコメントを `gh` で参照し、同種の指摘が再発していないか確認。

finder が使えない環境（Agent/Task ツール不可）では、同じレンズを自分で順に通す。ただしその場合も各レンズを**独立した観点として明示的に**走らせ、混ぜない。

些細な差分は fan-out せず「特記事項」の fast path へ。

### Step 5: verify（指摘ごとの反証・confidence 採点）

Step 4 で集まった全指摘（重複は統合）に対し、**1 件ずつ**検証する。各指摘について:

1. **反証を試みる**: 「これは実際には問題ない」と示す反例を 1 つ構築しにいく。反例が作れたら破棄。
2. **失敗シナリオを具体化する**: `<具体的な入力・状態> → <誤った出力・挙動>` を書けるか。書けない指摘は Critical / Important に上げない。
3. **confidence を 0〜100 で採点する**（下記ルーブリック）。

confidence ルーブリック:
- **0**: 全く自信なし。軽い精査で崩れる誤検知、または差分外（既存）の問題。
- **25**: ある程度。実問題かもしれないが誤検知の可能性もあり、実在を検証できていない。規約由来なら、その規約が当該箇所を明示していない。
- **50**: 中程度。実在は確認したが nit か稀なケースで、PR 全体では重要度が低い。
- **75**: 高い。二重チェックし、実際に踏まれる可能性が高い実問題。既存アプローチでは不十分。機能に直接影響、または規約の明記事項。
- **100**: 確実。踏まれる頻度も高く、証拠が直接裏付ける。

**フィルタ**: Critical / Important に載せるのは **confidence 80 以上、かつ具体的失敗シナリオを書けたもの**のみ。差分外（既存）の問題、誤検知、linter/型検査級、下記「何をレビューしないか」該当は捨てる。Nits はこの 80 ゲートを通さないが、最小限・キャップ内に留める。

### Step 6: 出力（統合して報告）

生き残った指摘を優先度順に並べ、下記フォーマットで報告する。確信度が中程度の指摘には「〜であれば問題」と条件を明示する。Critical / Important が無ければ「重大な問題はなし。〜」と 1〜2 行で結論を述べる。

## レビューの心得

- **シカトしない、忖度もしない**: 重要な問題は遠慮なく指摘する。逆に「念のため」「気になっただけ」レベルのコメントは出さない。
- **「問題なし」を安売りしない**: リスクの高い変更（条件・状態遷移・async・終端性）に「整合している」「破綻はない」と書くときは、**状態を実際にトレースした根拠**（対応表・全状態の追跡）を持っていること。反例を探して見つからなかったときだけ「問題なし」と断定する。
- **失敗シナリオで語る**: Critical / Important は必ず「どの入力・状態でどう壊れるか」を伴う。書けないなら格を下げるか出さない。
- **Nit を埋め草にしない**: スタイル・命名の好みは Nit としてまとめる。Linter で機械的に解決すべき指摘はしない。
- **行番号で指摘する**: `path/to/file.ts:42` の形式。
- **解決策を提示する**: 問題だけ並べない。「こう直す」を 1〜数行で示す。曖昧な場合は選択肢を提示。
- **既存コードとの一貫性・契約**: 周辺の慣習・兄弟実装の契約に従っているかを必ず確認。「正解」でも周辺と食い違うなら触れる。
- **推測は明示する**: 「〜の可能性がある」「〜であれば問題」と書く。断定するなら根拠（行番号、参照先）を添える。
- **既に正しいものは褒めない、流す**: 「Good」「LGTM」等のコメントで埋めない。問題がなければそのセクションを書かない。

## 出力フォーマット

レビュー結果は次の構造で報告する。該当がないセクションは省略する。

```markdown
## レビュー対象
<range / file / PR を 1 行で>

## 前回指摘の解消状況
<過去のレビュー指摘が渡された場合のみ。解消 N / 未解消 M / 部分的 K と、未解消の一覧>

## Critical
バグ、データ破壊、セキュリティ事故、本番障害を引き起こすもの。マージ前に必須対応。

- `path/file.ts:L42` — 〈問題の要約〉
  〈詳細：何が、なぜ問題か〉
  **失敗シナリオ**: 〈具体的な入力・状態 → 誤った挙動〉
  **修正案**: 〈具体的な修正〉

## Important
誤った振る舞い、契約違反、テスト不足など、修正すべきもの。

## Nits
スタイル・命名の細かな指摘。最大 10 件まで。

## 良かった点
**特に非自明な良い判断があった場合のみ** 1〜2 項目記載。
```

## 何をレビューしないか / 誤検知の例

以下は指摘しない。finder / verifier もこれらを誤検知として扱う:

- フォーマッタ・Linter・型検査・コンパイラで機械的に捕まるもの
- 差分外（既存）の問題。変更行がその箇所を悪化させていない限り触れない
- 「個人的に好み」レベルの命名変更、senior が指摘しない衒学的な nit。
- 欠陥ではない「もっと良くできる」提案（設計・可読性・保守性の改善案）。修正案は指摘に添えるが、指摘を伴わない提案は出さない。
- 既知の TODO や負債（差分でその箇所が悪化していない限り）。
- 規約に反するが、コード側で明示的に抑止されているもの（lint ignore コメント等）。
- テスト網羅・一般的なセキュリティ・ドキュメント不足などの一般論（規約で明示的に要求されている場合を除く）。

## 特記事項

- **READ ONLY**: 変更は一切加えず、指摘のみ行う。検証しないと分からないことは懸念点として指摘する。
- **規模に応じたスケール（fast path）**: 差分が些細（おおむね 30 行未満・単一の明白な変更、設定 1 行など）なら fan-out せず1セッションでレビューする。ただし状態遷移・条件・async・終端性に触れる変更は規模に関わらず F4 の観点だけは必ず通す。
- **生成コード・ベンダーファイル**: `dist/`、`vendor/`、`*.lock`、自動生成ファイルはスキップする（差分があってもレビュー対象外と明記）。
- **不明点はユーザーに聞くとき**: 1 ファイル読めば分かることは読む。本当に意図が不明な箇所だけ、「〜の意図を確認したい」と末尾でまとめて聞く。
