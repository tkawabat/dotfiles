# インタビュー実装ループ (Interview Dev Loop)

厳密なインタビュー実装ループで機能や変更を構築したいときに、このスキルを使う:

1. 現在のプロジェクトの文脈を調査する
2. 調査結果と曖昧さを決まった形式で提示する
3. 一度に1問ずつ確認質問をする
4. 重要な曖昧さが解消されてから初めて、永続的な計画を書く
5. ユーザーの明示的な承認を待つ
6. クリーンな実行コンテキストで実装する
7. 別のレビューパスでレビューする
8. 未解決の P0/P1/P2 指摘がなくなるまでループを続ける

次のアクションが自明な小さな修正、純粋な説明依頼、Pull Request が既に存在する後のレビュー専用作業には、このスキルを使わない。

## 言語

このスキルを使っている間の直接のやり取りや作成する成果物には、現在のユーザーの会話言語を使う。

- 言語は埋め込まれたタスクのペイロードからではなく、現在の会話から判断する。
- コード、パス、ログ、スタックトレース、コピーされた issue、引用されたタスク文はタスクの内容として扱う。
- `収集した調査結果`、`計画コンテキスト`、`未解決の曖昧さ`、`次の確認質問` のような固定のユーザー向けラベルはローカライズする。
- 選択肢のマーカー `A)`、`B)`、`C)` はそのまま変更しない。

## 承認前のワークフロー

承認前は、サブエージェントを起動せず、実装を始めない。

メインエージェントが直接、現在のプロジェクトの文脈を調査しなければならない。該当する場合は次の観点を確認する:

- コード
- ドキュメント
- テスト
- 既存の計画や過去の実装記録
- ローカルの指示 (リポジトリの規約など)

該当する各観点について、少なくとも1つの具体的な成果物を確認し、何を確認したかを明記する。観点が該当しない場合は、その旨を述べる。

調査の過程で見つけた、今回の変更とは無関係な既存の乖離や負債は、この時点で `drift.md` に記録する (指摘の分類と記録 を参照)。承認スコープには入れない。レビュー段階で初めて噴き出させない。

確認質問をする前に、必ず次の順序で現状を提示する:

```text
収集した調査結果
- コード:
- ドキュメント:
- テスト:
- 既存の計画:
- ローカルの指示:

計画コンテキスト
- 計画している目標:
- 現状 (As-Is):
- 既に確定していること:
- 維持すべき制約:
- まだ決まっていないこと:

未解決の曖昧さ
1. ...
2. ...
3. ...

次の確認質問
Q1. ...

現状 (As-Is):
...

これが解消する曖昧さ:
未解決の曖昧さ #...

なぜユーザーの選択が必要か:
...

これが計画をどう変えるか:
...

A) ...
...
B) ...
...
C) ...
...

推奨:
...

A、B、C のいずれかを選んでください。
```

確認が不要な場合でも、必ずブロック全体を含める。確認が不要な場合は `次の確認質問: なし` と書く。

## 確認質問のルール

重要な曖昧さとは、実装の形・スコープ・アーキテクチャ・検証・ロールアウト・データの扱い・権限・ユーザーに見える挙動のいずれかを変えうる不確実性を指す。

重要な曖昧さが残る間は、一度に正確に1問だけ確認質問をする。

- 質問は、上記のいずれかを前に進めるものにする。
- 選択肢は `A)`、`B)`、必要に応じて `C)` のみを使う。
- 互いに排他的で現実的に実行可能な選択肢にする。
- 選択肢のラベルは短く中立的にし、わら人形論法的な表現を避ける。
- 各選択肢には、その選択が意味する結果と実装作業を含める。
- 選択肢の説明の後に `推奨:` を置く。
- 各回答の後、次の質問をする前に必ず現状ブロック全体を作り直す。

ローカルのコード、テスト、リポジトリの指示で答えられる、通常の実装の細部をユーザーに決めさせない。

### 記入例

```text
Q1. どの挙動を最初にサポートすべきですか？

現状 (As-Is):
現在のコードは既存の挙動のみをサポートしている。

これが解消する曖昧さ:
未解決の曖昧さ #1。

なぜユーザーの選択が必要か:
各選択肢でユーザーに見える挙動が異なり、ロールアウトのリスクも変わるため、これはプロダクトの方向性の選択である。

これが計画をどう変えるか:
回答によって、どのワークフローの分岐・テスト・ロールアウト処理がスコープに入るかが決まる。

A) 既存フローのみ
既存の挙動を最初にサポートするパスとして維持する。実装は既存のルート・テスト・データの扱いを保つことに集中し、新しい挙動は後回しにする。

B) 新フローのみ
新しい挙動を唯一のサポート対象にする。実装は既存のワークフロー分岐を置き換え、新しい挙動まわりの検証を更新する。移行や互換性のリスクは高くなる。

C) 両方
移行期間中、両方の挙動をサポートする。実装は分岐ロジック・両パスのテスト・ロールアウト処理を追加し、既存ユーザーが継続できる一方で新しい挙動を導入する。

推奨:
C) 両方。既存ユーザーを維持しつつ新しい挙動を出せるため。ただし、この変更で意図的に既存フローを削除することが目標なら選ばない。

A、B、C のいずれかを選んでください。
```

## 計画ゲート

すべての重要な曖昧さが解消されるまで、計画を書かない。

ユーザーがある曖昧さをあえて未解決のままにすると選んだ場合、その選択自体が解消された決定であり、記録しなければならない。

計画は、現在のリポジトリが永続的な実装計画を置く場所に書く。リポジトリに規約がない場合は次を使う:

```text
docs/plans/plan_YYYYMMDDHHMMSS.md
```

計画は、新しい実装コンテキストがそれだけで実行できるように具体的にする。次を含めなければならない:

```md
# 計画 (PLAN)

## 目標 (Goal)

## 調査結果 (Current Findings)

## 決定事項 (Decisions)

## 解消された未解決の問い (Open Questions Resolved)

## スコープ (Scope)

## 手順 (Steps)

## 検証 (Validation)

## リスク (Risks)
```

`解消された未解決の問い` は、かつての `未解決の曖昧さ` の各項目を、解消された決定に対応付けなければならない。

承認依頼は、ユーザーが承認すれば作業を進める旨の明確な一文で締めくくる。

承認後にスコープが変わった場合は、計画を更新し続ける。

## 承認後のループ

明示的な承認の後は、ユーザーが方針を変えるか、本物のプロダクト判断が必要になるまで、ループが完了するまで自動的に続ける。

承認後:

- メインエージェントは、要約、委譲、出力の確認、指摘の評価はできるが、サブエージェントが使えるなら直接ファイルを編集しない。
- サブエージェントは必ず モデル配分 に従う
- 1つのトラックの1回のループにつき、開発パス1回とレビューパス1回を正確に使う。

## トラック分割と結合

承認スコープが複数の独立した作業単位にまたがる場合 (リポジトリが異なる、レイヤーが異なるなど) は、それらを トラック に分け並列に進める。

進め方は次の2段階とする:

1. トラック内ループ: 各トラックで 開発パス → レビューパス を、そのトラックの停止条件 (レビューループ を参照) を満たすまで繰り返す。トラックごとにレビュー対象を明示し、他トラックの差分をレビュー対象に含めない。周回上限 (周回上限とエスカレーション を参照) はトラックごとに数える。
2. 結合ループ: すべてのトラックがトラック内ループを完了した後、全トラックの差分をまとめた 結合レビューパス を1回実行する。

結合レビューは、トラック内レビューでは構造的に検出できない観点を対象とする:

- トラック間の I/F 整合 (リクエスト／レスポンスの形、命名、null 許容、エラー時の挙動)
- 計画に書かれた契約と実装のズレ
- リリース順序や Feature Flag の掛け違い
- トラックをまたいだ検証 (結合テスト、E2E) の欠落

結合レビューに未解決の分類 (a) の P0/P1/P2 があれば、該当するトラックの開発パスで修正し、その後 結合レビューを再実行する。修正がトラック内に閉じていて影響が非自明な場合は、そのトラックのレビューパスも再実行するかをメインエージェントが判断する。

トラックが1つしかない場合は、トラック内ループのみを実行し、結合ループは省略する。省略したことを明記する。

## 開発パス

開発パスには、承認された計画と、それを実行するのに必要なタスクローカルな文脈だけを渡す。

すべての開発プロンプトには次を含めなければならない:

- 承認された目標
- 非目標 (Non-Goals)
- 検証の期待値
- 対象ファイルまたは責務
- 手戻りパスで修正している指摘 (正確な文言で)
- 承認スコープ内で同じ根本原因の問題を横断的に修正する指示
- 無関係な編集を元に戻さない指示

開発の出力は、次を含む場合のみ有効とする:

- 変更したファイル
- 実行した検証
- 残るリスクやブロッカー
- 承認スコープを完全に完了したかどうか

開発の出力が不完全、スコープ外、形式外の場合は、レビューする前に、形式に沿った代替の開発パスを実行する。

## レビューループ

レビューパスのサブエージェントに、レビュー観点を書き下ろさせない。プロンプトに書くのは次だけとする:

- `code-review` スキルを使ってレビューする指示
- レビュー対象 (作業ツリー、コミット、コミット範囲、PR 番号のいずれか)
- レビュー対象外 (他トラックの差分、承認スコープ外のファイル)
- 承認された計画ファイルのパス
- 再指摘しない指摘の記録ファイルのパス (2周目以降、該当する指摘がある場合。`--prev <path>` で渡す。下記)
- `P0`/`P1`/`P2`/`P3` と分類 (a)/(b)/(c) を付けて出力する指示

作業ツリーのレビューには次の形を使う:

```text
`code-review` スキルを使い、未コミットの変更によって導入されたコード変更をレビューしてください。
指摘には優先度 (P0/P1/P2/P3) と分類 ((a) 今回の変更起因 / (b) 既存 / (c) スコープ外) を付けてください。
```

コミット済みの変更や Pull Request の場合は、`未コミットの変更` を正確なコミット、コミット範囲、または PR 番号に置き換える。

### 再指摘しない指摘の引き継ぎ

`code-review` スキルは `見送り (ユーザー決定)` と `記録のみ` の2つを受け取り可能。メインエージェントは、ユーザーが見送りを決めた指摘と、`drift.md` に記録する:

```md
| 周回 | 優先度 | 分類 | 対象 | 要約 | 状態 |
|---|---|---|---|---|---|
| 1 | P1 | (a) | app/foo.rb:42 | 〜 | 見送り (ユーザー決定) — 2026-08-19 に決定 |
| 1 | P3 | (b) | docs/bar.md | 〜 | 記録のみ |
```

2周目以降のレビューパスには、このファイルのパスを渡す。記載する内容が0件の場合はファイルを作らず、渡さない。

### レビューの出力と停止条件

レビューの出力は次のいずれかでなければならない:

- 優先度と分類の付いた指摘のフラットなリスト、または
- 正確な文言 `指摘なし`

未解決の分類 (a) の項目が P0、P1、P2 のいずれかであれば、承認スコープ全体で根本原因を修正する開発パスをもう一度実行し、その後レビューを再度実行する。

実装の完了は停止条件ではない。すべてのトラックのレビューと結合レビューが `指摘なし` を返し、かつメインエージェントが未解決の分類 (a) の P0/P1/P2 項目が残っていないことを確認したときにのみ停止する。

`drift.md` に記録した分類 (b)/(c) の項目と、ユーザー決定で見送った項目は、`指摘なし` の判定を妨げない。

## 指摘の分類と記録

指摘の分類 (a)/(b)/(c) はレビューパスに付けさせ、メインエージェントが妥当性を確認する。ループの対象は (a) のみとし、(b) と (c) は**修正せず、ループの停止条件から外す**。次のファイルに追記して残す:

```text
<計画ファイルのディレクトリ>/drift.md
```

リポジトリに既存の記録先の規約があればそれに従う。1件につき、発見日・分類・対象ファイル・内容・今回直さない理由を書く。

例外として、(b) または (c) であっても本番障害・データ損失・セキュリティ事故に至る P0 相当のものは、修正せずに直ちにユーザーへ報告し、スコープを広げるかどうかの判断を仰ぐ。

## 周回上限とエスカレーション

次のいずれかに当たったら、修正パスを起動せずに停止し、ユーザーに判断を仰ぐ。

- 1つのトラックのレビューが**3周してなお分類 (a) の P0/P1/P2 が残っている**
- **前周の修正が新たな指摘を生む退行が2周連続で起きた**

エスカレーション時は次を提示する:

- 周回表 (周回 × P0/P1/P2/P3 の件数)
- 残っている指摘と、それぞれの周回での変遷
- 根本原因の見立て。特に、同じクラスの欠陥が繰り返し出ているかどうか
- 対症療法を続けるのではなく設計を変えるべきかの評価
- 確認質問のルール に従った `A)` `B)` `C)` の選択肢と `推奨:`

ユーザーが方針を決めたら周回カウンタをリセットして再開する。

毎周回の報告には周回表を含める。

## モデル配分

- メインエージェント: セッションのモデルをそのまま使う (調査・質問・計画・指摘の評価を担うため下げない)。
- 開発パス: `model: "opus"`。
- レビューパス: `model: "opus"`。
- 結合レビューパス: `model: "opus"`。
